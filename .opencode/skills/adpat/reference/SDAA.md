# 模型的适配迁移
先仔细阅读仓库中的README.md文档。
然后在深度的对项目进行深度了解。
然后看看这个项目需不需要模型，需要模型的话对这个模型进行深度分析。
将模型迁移到SDAA上的方法参考：reference/手动迁移、reference/自动迁移、reference/迁移约束
迁移后这个项目是要能够支持CPU/CUDA/SDAA三个平台的。还有判断有无自定义的算子。

# 项目规范性
在适配的过程中，要在当前项目的目录下新建一个'linshi'的目录，适配产生的文件都在这个目录下面，并且要有子目录进行隔离文件与文件，避免最后特别乱。
这样做可以保证原项目结构的不变，更干净。还有就是如果需要修改代码，修改完后需要在最后整个完整的过程结束后，通过git生成一个patch放在，一个新建的目录‘SDAA’下面，保存在patches这个目录下面。

# 评估测试
迁移完成后，在通读项目找到官方的评测脚本，以及权重下载路径还有评测需要的数据集，同时还有评测的指标（评测指标只能使用官方仓库指定的，不能自己创造指标）。

补充：在进行评测时，需要在推理脚本上添加上一个功能用来记录：推理速度、测试时间、显存的使用情况，以及CPU的使用情况。添加这个功能不能影响测试脚本原来的功能。

如果没提供评测脚本，你就根据项目的理解，来实现评测的脚本。
如果提供权重的下载路径，你先尝试下载，如果无法下载，需要进行报告并提供下载的地址，然后我来下载。
对于数据集也是，如果项目中提供了，就是用项目中的。如果没提供，则看官方有没有提供下载地址，有的话你先进行尝试下载，如果无法下载则进行报告并提供下载的地址，我来下载。


# 评测入口
要在`linshi`这个目录下面新建一个`eval_script`目录
这个目录下面，只放，评测脚本以及这个脚本的报告，主要是报告：1. 这个脚本是不是官方提供的，如果不是要说明这个脚本的来源依据。2. 这个脚本是用来评测什么的，也就是这个评测的目的。3. 这个脚本使用的评测指标是什么，是不是官方指定的。

补充：对于官方没给评测脚本，你根据对项目的理解，实现的评估脚本，要在文档中注明，是根据项目来实现的评测脚本，也注明实现的参考来源。

# 报告
1. 评测结束后，要在当前项目的目录下新建一个'linshi'的目录，后面产生的任何调试、日志文件都按类新建子文件夹并放入对应的子文件夹中。
评测的报告保存在`linshi/pc_report/`下面。报告中，要报告出在各个数据集上的指标评测结果。格式就是一个表格里面有使用的模型、数据集、指标、以及各个指标的结果，就是和一篇论文的主实验的实验数据表格类似。
还有性能的结果也保存在这个报告中，性能包括，推理时间，显存占用情况。

2. 对于使用的数据集、指标（以及每个指标的含义）、使用的权重，这些也生成一个报告。放在`linshi/zonghe_report`下面。

3. 适配过程中以及运行这个项目时需要的依赖，踩的坑，改动的内容也要生成一个报告。放在`linshi/change_report`下面。

# Agent运行评测指南
在生成一个Agent运行评测这个项目的指南：Agent可以根据这个指南，能够很快速的运行评测。要能够针对CPU/CUDA/SDAA平台。环境不一样，但是运行的脚本，输出的结果格式要一致，这样最后我能够来对比各个平台之间的结果。不同平台根据这个能进行运行评测这个项目。这个保存在`linshi/agent_guid`下面。

# 项目整理
当全部完成后，要在项目中给出一个如何使用评测脚本的文档，要在文档中写清楚，使用哪些数据集，使用哪些权重，以及使用脚本需要哪些参数，每个参数的意思是什么，还有评估的指标是什么
对于官方没给评测脚本，你根据对项目的理解，实现的评估脚本，要在文档中注明，是根据项目来实现的评测脚本，也注明实现的参考来源。
